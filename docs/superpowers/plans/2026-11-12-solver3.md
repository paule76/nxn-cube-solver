# Teilprojekt B: 3x3-Solver – Implementation Plan

> **For agentic workers:** Execute task-by-task (executing-plans, inline). `bd` is not available here; git history on `feature/solver3` is the record. **Task 7 (merge to `main`, 2x2-Hinweis) erst nach ausdrücklicher Freigabe durch den Nutzer.**

**Goal:** Eigener Kociemba-Zwei-Phasen-Solver für den 3x3 (meist ≤ 20 Züge), im Web Worker mit IndexedDB-Cache, eingebunden in die App inkl. Zufallszustands-Mischung.

**Architecture:** Reine Solver-Module unter `src/solver3/` (Node-testbar); ein Worker baut/lädt Tabellen und löst; ein Client kapselt Nachrichten als Promises; `src/solvers.js` gibt der App eine einheitliche async-Schnittstelle je Größe.

**Tech Stack:** ES-Module, Module Worker, IndexedDB, `node --test`, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-12-solver3-design.md`

## Global Constraints
- Keine Abhängigkeiten, kein Build; 2x2 unverändert; alle bisherigen Tests grün.
- Suche: Abbruch bei Länge ≤ 20 oder nach 500 ms (beste bis dahin).
- IndexedDB: DB `cube-solver`, Store `tables`, Schlüssel `cube3-tables-v1`; jeder Zugriff fehlertolerant.
- Neue Texte DE + EN; `msg.validNoSolver` entfällt.
- Puzzle-Module bleiben synchron und rein (`cube3.solve` bleibt `undefined`); Async-Lösen liegt in `src/solvers.js`.

### Task 2: Tabellen

**Interfaces:**

- `buildTables() -> Tables` mit `twistMove, flipMove, sliceMove` (`Uint16Array`, n×18), `cpermMove, udepermMove` (n×10), `spermMove` (24×10, Phase-2-Züge) sowie Pruning `pTwistSlice, pFlipSlice, pCpermSperm, pUdepermSperm` (4 Bit/Eintrag, `Uint8Array`, Größe ⌈n/2⌉) und `prune(table, index) -> depth`

### Task 3: Suche und Zufallszustand
**Files:** Create `src/solver3/search.js`, `src/solver3/random-state.js`, `test/solver3-search.test.js`

**Interfaces:**
- `createSearch(tables) -> { solve(state, { maxLength = 20, timeoutMs = 500, now = () => performance.now() }) -> Move[] }`
  - Phase 1 IDA* (Heuristik = max der beiden Pruning-Werte), Zugregeln: nie gleiche Seite hintereinander; Gegenseiten nur in Reihenfolge U<D, R<L, F<B (d. h. nach D kein U).
  - Bei Phase-1-Ziel: Phase-1-Folge auf den vollen Zustand anwenden (`applyMoves3`), Phase-2-IDA* mit Schranke `best − l − 1` (max. 18); Phase-1-Folgen, deren letzter Zug ein Phase-2-Zug ist, überspringen (außer l = 0).
  - Ergebnis = beste gefundene Gesamtfolge; Abbruch, sobald Länge ≤ `maxLength` oder Zeit > `timeoutMs` und mindestens eine Lösung existiert.
- `randomState(rng = Math.random) -> state` (Fisher-Yates für `cp`, `ep`; bei Paritätsunterschied `ep[10]`/`ep[11]` tauschen; `co[0..6]`, `eo[0..10]` zufällig, letzte so, dass Summe passt)
- `inverseMoves(moves) -> Move[]` (Reihenfolge umkehren, `turns` 1↔−1, 2 bleibt)

**Acceptance Criteria:** gelöster Zustand → `[]`; ein Zug → Länge 1; 200 `randomState()`: `isSolved3(applyMoves3(s, solve(s)))`, Mittelwert ≤ 21, Maximum ≤ 24; `parse3(toFacelets3(randomState()))` immer ok (1000×); Positionsverteilung von Kante 0 über 12000 Zustände: jede Position 1000 ± 150; `applyMoves3(SOLVED3, inverseMoves(solve(s)))` = `s`.

- [ ] Tests → FAIL → implementieren → PASS → Commit `feat(solver3): two-phase search and random states`

### Task 4: Worker, Client, Cache, Solver-Adapter
**Files:** Create `src/solver3/worker.js`, `src/solver3/client.js`, `src/solver3/cache.js`, `src/solvers.js`, `test/solver3-client.test.js`

**Interfaces:**
- `cache.js`: `loadTables() -> Promise<Uint8Array|null>`, `saveTables(bytes) -> Promise<void>` (IndexedDB wie in Global Constraints; jede Ausnahme → `null` bzw. still).
- `worker.js` (Module Worker): beim Start `loadTables()` → `importTables` (bei Fehler: `buildTables()` + `saveTables(exportTables(t))`) → `postMessage({type:'ready', cached:boolean})`; Nachrichten `{type:'solve', id, state}` → `{type:'solution', id, moves}`; `{type:'randomScramble', id}` → `{type:'scramble', id, moves}` (= `inverseMoves(solve(randomState()))`); Fehler → `{type:'error', id?, message}`. Züge als `{face, turns}`.
- `client.js`: `createSolverClient(worker) -> { ready: Promise<void>, get isReady, get failed, solve(state) -> Promise<Move[]>, randomScramble() -> Promise<Move[]> }` – ordnet Antworten über `id` zu; `error` ohne id oder `worker.onerror` → `failed = true`, `ready` wird abgelehnt, offene Promises abgelehnt. Rückgabe-Züge werden auf Objekte aus `ALL_MOVES` abgebildet.
- `solvers.js`: `createSolvers({ createWorker = () => new Worker(new URL('./solver3/worker.js', import.meta.url), { type: 'module' }) }) -> { get(id) -> { isReady, failed, whenReady(): Promise, solve(state): Promise<Move[]>, randomScramble?(): Promise<Move[]> }, start(id) }` – `'2x2'` sofort bereit (nutzt `cube2.prepare/solve`), `'3x3'` startet den Worker erst bei `start('3x3')`.

**Acceptance Criteria (Node, Fake-Worker mit `postMessage`/`onmessage`):** `ready` löst nach `ready`-Nachricht; Antworten werden per id korrekt zugeordnet (zwei gleichzeitige Anfragen, Antworten in umgekehrter Reihenfolge); `error` → `failed` und abgelehnte Promises; Züge sind `ALL_MOVES`-Instanzen. Worker + Cache werden in Task 5 per e2e geprüft.

- [ ] Tests → FAIL → implementieren → PASS → Commit `feat(solver3): worker, client and IndexedDB cache`

### Task 5: Einbindung in die App
**Files:** Modify `src/app.js`, `src/i18n.js`, `index.html` (falls Texte), Create `e2e/solve3.e2e.js`

**Verhalten:**
- `solvers = createSolvers()`; beim Anzeigen des 3x3 (Start oder Wechsel) `solvers.start('3x3')`.
- `solve()` wird async mit Anfrage-Token `{ size, inputVersion }`; `inputVersion` erhöht sich bei jeder Eingabeänderung, beim Mischen, Zurücksetzen, Leeren. Antwort nur übernehmen, wenn Token aktuell.
- Nicht bereit: `msg.preparing3`, nach `whenReady()` automatisch lösen (gleiches Token). Suche: `msg.searching`. Fehler: `msg.solverFailed`.
- Stepper je Größe: `sessions[id].stepper = createStepper(view, () => sessions[id].solution)`; `goTo` nutzt den Stepper der aktiven Größe.
- Mischen 3x3: bereit → `await solver.randomScramble()`; sonst `puzzle.scramble()`.
- Texte DE/EN: `msg.preparing3`, `msg.searching`, `msg.solverFailed`; `app.lead`/`meta.description` ergänzen um „2x2: kürzeste Lösung · 3x3: kurze Lösung (meist ≤ 20 Züge)“; `msg.validNoSolver` entfernen.

**Acceptance Criteria (e2e):**
- 3x3 mischen → lösen → Lösung 1–24 Züge → „Ende“ → jede Seite einfarbig, 3D == Netz.
- Zweiter Seitenaufruf im selben Browser-Kontext: Solver bereit ohne Vorbereitungsphase (Test: Zeit von Laden bis „Bereit.“ < 1500 ms, und Meldung `msg.preparing3` erscheint nicht).
- Neuer Kontext, sofort „Lösen“ auf gemischtem 3x3 → zuerst „3x3-Solver wird vorbereitet …“, danach automatisch „Lösung gefunden: …“.
- Lösen starten, sofort auf 2x2 wechseln und zurück → keine Lösung des alten Auftrags angezeigt, wenn sich die Eingabe inzwischen geändert hat (Netzklick vor dem Zurückwechseln).
- Alle bisherigen e2e grün (`sizes.e2e.js`-Erwartung „Gültiger Würfel …“ wird durch echte Lösung ersetzt).

- [ ] Implementieren; Unit + e2e grün; Commit `feat: solve the 3x3 in the app`
